# 0005: Auth: JWT for users, API keys for clients, gateway verification

- **Status:** Superseded by [0014](0014-auth.md) (2026-11-22); kept unchanged below as history
- **Date:** 2026-11-22
- **Deciders:** Jay Pascual

## Context

Three kinds of callers: dashboard users, API clients, and services calling each other
(often from workers with no user request). Services must be able to trust who is
calling and for which org without each one reimplementing auth.

## Decision

- **accounts is the only token issuer.** One JWT format (EdDSA, keys rotated, public
  keys at accounts `/.well-known/jwks.json`) for all callers. Claims: `iss`, `sub`,
  `typ` (`user`, `api_key`, `service`), `org`, `role` (users) or `access` (API keys),
  `iat`, `exp`, `jti`.
- **Users:** email and password at `/v1/auth/*` (passwords hashed with Argon2id).
  Access token 15 minutes, opaque refresh token 30 days, rotated on every use with
  reuse detection. A token is scoped to one org; `POST /v1/auth/refresh {orgId}` switches.
- **API clients:** `X-API-Key: rex_live_<32 base62>` (or `rex_test_`). Stored as a hash;
  shown once. Access `read` or `read_write`. Only the gateway accepts raw keys and
  exchanges them at `POST /internal/v1/api-keys/exchange` for an access token of at most
  5 minutes, cached; `api_key.revoked` evicts the cache.
- **Gateway:** verifies tokens (JWKS cached), exchanges API keys, rate limits, strips
  inbound `X-Rex-*` headers, and forwards `Authorization: Bearer <access token>`.
- **Services:** verify the token again with `packages/auth` (defense in depth), enforce
  per-operation security from their spec (some free-tool operations allow anonymous),
  check role/access, and scope every query to the token's `org`.
- **Service to service:** client credentials at `POST /internal/v1/service-tokens`
  (`typ: service`, `sub: svc:<name>`). A worker acting for a tenant passes the org it
  acts for from the event envelope; services accept a service token plus an explicit
  org only on internal operations.
- Roles are org-wide: owner, admin, member, viewer.

## Consequences

- One verifier library, one token format, one JWKS: no per-service auth code.
- accounts is on the critical path only for API key exchange on cache misses and for
  login; JWKS caching keeps it off the hot path.
- SSO (Google, SAML) and per-project permissions are later additions to accounts.

## Alternatives considered

- **Gateway-minted internal tokens**: a second issuer and key set to manage.
- **Trusting gateway headers (`X-User-Id`) without signatures**: unsafe if anything
  inside the cluster is compromised or misrouted.
- **Third-party identity (Auth0, Clerk, Cognito)**: faster start, recurring cost and less
  control over API key exchange and service tokens; revisit if SSO arrives early.
- **mTLS / service mesh identity**: stronger transport identity; can be added in Phase 7
  on top of service tokens.
